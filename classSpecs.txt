2. "screen" Command Support [cite: 60]
   From the main menu, the user can perform the following:
   * Create a new process via "screen -s <process name>" command[cite: 60].
   * Lists all running processes via "screen -ls" command[cite: 60].

3. Barebones Process Instructions [cite: 60, 62]
   Support basic process instructions, akin to programming language instructions:
   * PRINT(msg) - display an output "msg" to the console. The output can only be seen when the user is inside its attached screen[cite: 60]. The "msg" can print 1 variable, "var." E.g. PRINT("Value from: " + x)[cite: 60].
   * DECLARE(var, value) - declares a uint16 with variable name "var", and a default "value"[cite: 60].
   * ADD (var1, var2/value, var3/value) - performs an addition operation: var1 = var2/value + var3/value[cite: 60]. Variables are automatically declared with a value of 0 if they have not yet been declared beforehand. Can also add a uint16 value[cite: 60].
   * SUBTRACT (var1, var2/value, var3/value) - performs a subtraction operation: var1 = var2/value - var3/value[cite: 60].
   * SLEEP (X) - sleeps the current process for X (uint8) CPU ticks and relinquishes the CPU[cite: 60].
   * FOR([instructions], repeats) - performs a for-loop, given a set/array of instructions. Can be nested[cite: 60].

   Notes:
   * Process instructions are pre-determined and not typed by the user (e.g., randomized via scheduler-start)[cite: 60].
   * Variables are stored in memory and will not be released until the process finishes[cite: 62].
   * uint16 variables are clamped between (0, max(uint16))[cite: 62].
   * Unless specified in the test case, the "msg" in the PRINT function should always be "Hello world from <process_name>!"[cite: 62].
   * For loops can be nested up to 3 times[cite: 62].

4. Generation of CPU Utilization Report [cite: 62]

5. Configuration Setting [cite: 62]

THE "SCREEN" COMMAND SPECIFICATIONS
--------------------------------------------------------------------------------
The "screen" command emulates the screen multiplexer of Linux OS[cite: 64]. 
* When the user types "screen -s <process name>" from the main menu console, the console will clear its contents and "move" to the process screen[cite: 149].
* At any given time, any process can finish its execution. If this happens, the user can no longer access the screen after exiting[cite: 159, 160].
* The user can access the screen anytime by typing "screen -r <process name>" in the main menu[cite: 161]. If the process name is not found/finished execution, the console prints "Process <process name> not found."[cite: 162].

Inside the Process Screen, the user can type[cite: 150]:
* "process-smi" - Prints a simple information about the process[cite: 151]. The process contains dummy instructions that the CPU executes in the background[cite: 152]. Whenever the user types "process-smi", it provides the updated details and accompanying logs from the print instructions[cite: 153]. If the process has finished, simply print "Finished!" after the process name, ID, and logs have been printed[cite: 154, 155].
* "exit" - Returns the user to the main menu[cite: 156].


THE "SCHEDULER-START" AND "SCHEDULER-STOP" COMMANDS
--------------------------------------------------------------------------------
* "scheduler-start" - Every X CPU ticks, a new process is generated and put into the ready queue for your CPU scheduler[cite: 166]. This frequency can be set in the "config.txt"[cite: 167]. As long as CPU cores are available, each process can be executed and be accessible via the "screen" command[cite: 167]. You must generate human-readable process names (E.g.: p01, p02, ..., p1240)[cite: 170, 171].
* "scheduler-stop" - Stops generating dummy processes[cite: 168].
These commands are only accessible in the main menu console[cite: 169].


THE "SCREEN -LS" AND "REPORT-UTIL" COMMANDS
--------------------------------------------------------------------------------
These commands should be similar. The only difference is that "report-util" saves this into a text file - "csopesy-log.txt." [cite: 173]
* Output must list CPU utilization, cores used, and cores available[cite: 251].
* Output must print a summary of the running and finished processes[cite: 251]. Note that all finished and currently running processes must be reported[cite: 163].


THE SCHEDULER & CPU TICKS
--------------------------------------------------------------------------------
Your CPU scheduler is real-time and will continuously schedule processes as long as your console is alive[cite: 255]. The scheduler algorithm will be set through the "initialize" command and through the "config.txt" file[cite: 256].
* For simplicity, assume that the CPU tick is an integer counter that tallies the number of frame passes[cite: 258].


THE CONFIG.TXT FILE AND "INITIALIZE" COMMAND
--------------------------------------------------------------------------------
The user must first run the "initialize" command[cite: 273]. Once entered, it will read the "config.txt" file, which is space-separated in format, containing the following parameters[cite: 274]:

* num-cpu: Number of CPUs available. The range is [1, 128][cite: 275].
* scheduler: The scheduler algorithm: "fcfs" or "rr"[cite: 275].
* quantum-cycles: The time slice is given for each processor if a round-robin scheduler is used. Has no effect on other schedulers. The range is [1, 2^32][cite: 275].
* batch-process-freq: The frequency of generating processes in the "scheduler-start" command in CPU cycles. The range is [1, 2^32]. If one, a new process is generated at the end of each CPU cycle[cite: 275].
* min-ins: The minimum instructions/command per process. The range is [1, 2^32][cite: 275].
* max-ins: The maximum instructions/command per process. The range is [1, 2^32][cite: 275].
* delay-per-exec: Delay before executing the next instruction in CPU cycles. The delay is a "busy-waiting" scheme wherein the process remains in the CPU. The range is [0, 2^32]. If zero, each instruction is executed per CPU cycle[cite: 275].
