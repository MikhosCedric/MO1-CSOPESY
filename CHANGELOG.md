# CHANGELOG

All notable changes to this project will be documented in this file.

### [08-02-2026] - Global Memory Manager (Demand Paging)

**What was changed:** Added a new `MemoryManager` component that handles the emulator's physical memory as a global pool of frames. Each process gets a page table instead of a fixed private allocation. Pages are loaded into physical frames on demand (`prefetchPage`) and evicted using FIFO when memory runs out. Evicted pages are written to a backing store file (`csopesy-backing-store.txt`) and read back on demand. The manager also keeps track of total, used, active, inactive, and free memory and counts pages paged in/out.

**Why it was changed:** The specification (Section 4) replaces the MO1 fixed per-process allocation with global virtual memory management. Memory is divided into frames, allocated globally across processes, and pages are swapped to a backing store when physical memory is exhausted.

---

### [08-02-2026] - Memory Configuration & Validation

**What was changed:** Added `max-overall-mem`, `mem-per-frame`, `min-mem-per-proc`, and `max-mem-per-proc` to the configuration file and its parser/validator. All values must be powers of 2 within the range [64, 65536] bytes, the frame size must evenly divide the overall memory, and minimum process memory cannot exceed maximum. The initialization message now prints the memory settings.

**Why it was changed:** The specification (Sections 3.1, 3.3, 4.1) defines these memory parameters and their validation rules (power-of-2 format, valid range), which must be enforced on load.

---

### [08-02-2026] - New Instructions (READ, WRITE)

**What was changed:** Added `READ` and `WRITE` instruction opcodes to the process instruction set, along with access-violation tracking. `WRITE` copies a value to a memory address; `READ` copies a value from a memory address. Any access to an address outside the process's memory allocation shuts the process down with an access-violation error, recording the offending address and the time it occurred.

**Why it was changed:** The specification (Section 5) defines `READ` and `WRITE` as new instructions, and Section 3.5 requires access-violation handling that reports the invalid hex address and the shutdown timestamp.

---

### [08-02-2026] - Process Screen Updates (`screen -s`, `screen -c`, `screen -r`)

**What was changed:** `screen -s` now validates the requested memory size and prints `invalid memory allocation` when it is outside the valid range or not a power of 2. `screen -c` creates a process from 1-50 semicolon-separated instructions (printing `invalid command` otherwise) and accepts an optional memory size; when omitted, the size is auto-computed as the smallest power-of-2 allocation that covers the highest referenced memory address. `screen -r` now reports `Process <name> shut down due to memory access violation error that occurred at <HH:MM:SS>. <hex> invalid.` when attaching to a process that terminated from an access violation, and `Process <name> not found.` for unknown/finished processes.

**Why it was changed:** The specification (Sections 3.3, 3.4, 3.5) defines these commands, their validation messages, the auto-size behavior for created processes, and the updated terminal-attach logic for terminated processes.

---

### [08-02-2026] - `scheduler-test` Alias

**What was changed:** The `scheduler-test` command was added as an alias for `scheduler-start`, with configurable instruction counts and an explicit scheduler choice.

**Why it was changed:** The specification (Sections 3.1 and 6.2) lists `scheduler-test` as the command to start the scheduler for batch testing.

---

### [08-02-2026] - Batch Process Memory Size

**What was changed:** Batch processes generated by the scheduler now receive a random memory size that is a power of 2 within the configured minimum/maximum per-process range.

**Why it was changed:** The specification (Section 4.1) requires each process to be allocated a power-of-2 memory size within the configured bounds.

---

### [08-02-2026] - `process-smi` Global View & `vmstat`

**What was changed:** `process-smi` in the main menu now shows a global system view: CPU utilization percentage, total memory usage in MiB and as a percentage, and each running process with its memory footprint. `vmstat` reports total/used/active/inactive/free memory in KB plus idle/active CPU ticks and pages paged in/out. The timestamp format was updated to `MM-DD-YYYY`.

**Why it was changed:** The specification (Sections 3.6, 3.7, 3.8) defines these outputs for monitoring memory and scheduling activity across all processes.
